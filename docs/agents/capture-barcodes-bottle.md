# Capture: barcodes and bottle recognition

Covers barcode resolution (#21, #325) and the guided bottle recognition flow (Bottle Flow slice A, `BOTTLE_CAPTURE_ENABLED`).

## Barcodes

**Barcodes (#21, #325):** a scanned code resolves in one round trip. `lib/barcodes.ts` `normalizeGtin` gives every code one canonical key (UPC-A = 0-prefixed EAN-13 = 00-prefixed GTIN-14 = its UPC-E; EAN-8/13 as is; SKU junk and odd lengths rejected; a wrong check digit is kept and logged, not rejected). Catalog `barcode` rows hang off a SKU of the shade (`barcode.source` `ingestion`/`backfill`, `external_product_id`; migration 20261019030000000_barcode-provenance-and-user-barcodes): Shopify-style ingestion links the product GTIN and every variant barcode (`materializeProductBarcodes`), and `POST /api/barcodes-admin/backfill` (`npm run backfill:barcodes`, dry run by default) does it for products stored earlier. A GTIN belongs to one shade (`barcode.gtin` UNIQUE): the first shade keeps it, later claims are skipped and logged in the job log. The capture resolver tries catalog barcodes, then the caller's own learned `user_shade_barcode`, then connector products' raw `external_product.gtin` → `shade_source_product` → one active shade (fallback until the backfill has run). A `barcode` frame with a valid on-device decoded `quality.gtin` skips OCR and its response carries `check` (the read-only verdict, with a display `hex`); a `quality.gtin` on a frame the pipeline also read (a bottle photo with its sticker in view) is still the frame's GTIN evidence unless the pipeline read a code itself (`extractFrameEvidence`). A session that scanned an unknown GTIN and was matched another way (label, candidate, typed name), or a manual add carrying `barcode` (`POST /api/polishes`), remembers the GTIN in `user_shade_barcode`, private to that user and never in the shared catalog. The bottle flow's one-tap create sends `captureId` to `POST /api/polishes`, which in the same transaction marks the caller's session `matched` with the new shade (`lib/capture-session.ts`; unknown/foreign session 404, cancelled 409, both rolling the create back), learns the session's scanned GTIN unless the body carries its own `barcode`, and releases the session's frame blobs after commit.

## Bottle recognition

**Bottle recognition (Bottle Flow slice A, behind `BOTTLE_CAPTURE_ENABLED`, default off):** Rapid Add's guided bottle capture on the existing capture API. A photo has a *surface* (`front`, `bottom`, `glass`, `box`; `quality.surface`; front/bottom/box are `label` frames, glass is `color`) and the server drives the sequence: `nextFrame` (a `CaptureFrameRequestSpec`, or `null` = ask nothing more, then call `/check`) is returned by `start`, `frame`, `check`, `status` (`null` once the session is `matched`/`unmatched`/`cancelled`) and by `answer` only for a `skipSurface` answer, planned by the pure `planNextFrame` in `lib/bottle-flow.ts` (nothing once a barcode matched; retry a poor frame that added no name, brand, GTIN or glass hex; then brand from the front or the box, name from the bottom; then every bottle is walked through the front (while no brand), bottom, glass and box (while no GTIN) until each is photographed or skipped, so a name match never ends the sequence early; then glass again to break a tie; each prompt at most twice, never past 6 frames or for a skipped surface) with its counters in `capture_session.metadata.bottle`; `POST /api/capture/{id}/answer` with `{ skipSurface }` skips any photo (409 on a `matched`/`unmatched`/`cancelled` session). A `color` frame is measured on the server (`lib/glass-color.ts`: palette chips of the lacquer measured on the guide region only, a client-sent `quality.guideRegion` or the default centre outline in `lib/frame-region.ts`, the model picks one or the top chip is used, and a chip near a skin tone is kept only when it dominates the region, so the hand is not stored while nude lacquers stay measurable; stored as `extracted.hex` with `extracted.source = "glass"`, which a client can never set), and a data-URL `label` frame is read with a closed-set vision call over the hinted/read brand's shade names, or, with no known brand, over the catalog's brand names (`brandListed`, `listCatalogBrandNames`: brands with an `active` color shade, never a `__`-prefixed test brand; a printed brand that misspells exactly one listed brand by at most 2 letters fills `brandListed`, `nearestListedBrand`; the model's separate `brandConfidence` is the frame's, and a brand the prompt named that the model echoes back is dropped) (a pick counts only with a printed name or brand; at high detail, the brand-only front read at low detail; on a closed set the sticker is first read without the list and the closed pick counts as `shadeNameListed` only when that independent, complete printed name agrees with it (`nameAgreement` ≥ 0.75, or the printed name spells it, the same letters in order or `nameAgreement` ≥ 0.92, and no closed call is made; the open read also reports `bottleBox` / `nameBox`, and a name off the held bottle or outside a client-sent `quality.guideRegion` is dropped, `nameLocation`), else it is an unverified `shadeNamePick`, a candidate only, because with the list in view the model reports its pick as the printed text; a partly hidden name (`nameComplete: false`) never matches; the front is read for its brand only, with the v2 wording, and its shade name never becomes the shade name, `surfaceReadsShadeName`, but it is kept as `frontShadeName`: a shade it spells is a candidate, and a match on another shade becomes a question; `lib/sticker-read.ts`, no model call without a usable brand or OCR). The brand-first resolver `resolveBottle` (`lib/bottle-resolver.ts`, `bottle-v1`) scopes candidates to the brand (typed hint > barcode > read; a typed batch hint is resolved with word similarity / name prefix, `resolveBrandFromText(…, { mode: "hint" })`, read text with plain trigram similarity, then a unique-prefix fallback: "kbs" → KBShimmer when exactly one brand starts so and it is not a whole word of the name), pools the brand's shades of every bottle category (`BOTTLE_POOL_PRODUCT_CATEGORIES`: color, topper, top/base coat, treatment, never accessory; color distance only for color shades), scores name (`pg_trgm`, lifted by the verified closed-set pick; an unverified pick or front name gets at most `candidateOnly` = 0.6) and OKLAB distance from the glass hex, and uses bands: a confident name matches, color only confirms or breaks ties and never matches alone, and no plausible candidate gives the create card (`unmatched` with no candidates and a `suggestedShade`; a brand read off the bottle, by OCR or the model, is `brandSource: "read"` and must be confirmed before it can create a shared brand; a hint/read mismatch is `brandConflict`). A client never sets `quality.ai` or `extracted.shadeNameListed` / `shadeNamePick` / `shadeNameComplete` / `brandConfidence` / `source` (stripped on ingest), nor `metadata.bottle` (dropped at start, flag on or off). A frame's `quality.guideRegion` (`CaptureGuideRegion`, the outline the client drew in 0–1 fractions of the frame as sent; else `DEFAULT_GUIDE_REGIONS`, `lib/frame-region.ts`) bounds the glass measurement and drops a printed name read far outside it; the web sends it for shutter/auto-shutter surface photos (`apps/web/src/lib/guide-region.ts`, mapped through the preview's `object-cover` crop), uploads and the mobile app send none. Frame bytes are kept as private blobs under `{userId}/capture/{captureId}/` until the session is `matched`/`unmatched` or the hourly sweep expires them (flag off, or a frame added to an already `matched`/`unmatched` session, keeps the `inline://` placeholder). Frame, check and `skipSurface` answer responses also carry `readSoFar` (`CaptureReadSummary`: barcode, brand with catalog match, shade name, glass hex, finish, and what the latest photo added), which the web shows as "What we've read" under the camera. Flag off: every response is exactly today's, with no `nextFrame` / `brandHint` / `suggestedShade` / `brandConflict` / `readSoFar`. See `packages/functions/README.md` → "Bottle flow".
