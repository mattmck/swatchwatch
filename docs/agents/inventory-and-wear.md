# Inventory, wear and collection stats

Covers inventory status rules (D5), wear stats derived from the mani log, collection stats and the wishlist value.

## Inventory status

**Inventory status:** each `user_inventory_item` has `status` (`owned | wishlist | destash | archived`, CHECK-constrained; `PolishStatus` / `POLISH_STATUSES` in `packages/shared`), `tried_at`, `last_worn_at` and `wear_count` (migration 20261017061336791_inventory-status). Ownership is only ever `status = 'owned'` (web: `isOwnedPolish` in `apps/web/src/lib/inventory-status.ts`); never infer ownership or wishlist from `quantity`. "Untried" is derived (`owned AND tried_at IS NULL`, `Polish.isUntried`), not a status. `GET /api/polishes` filters with `status=` (comma list) and `untried=true`; create/update validation lives in `packages/functions/src/lib/inventory.ts` (on update, `rating: null` and `purchaseDate: null` clear the stored value like `triedAt`/`purchasePrice`; a missing key keeps it). Polish responses carry `ownSubmitted` (true only for the caller's own private `user_submitted` shade). Status rules (decision D5): a new row without `status` is `owned` (only an explicit `quantity: 0` gives `wishlist`); running out archives (`status: "archived"`, reason `used_up`/`decluttered` stored as an `inventory_event`, see `planArchiveEvent`), never wishlists; only an explicit Rebuy / ♡ moves an archived polish to the wishlist; CSV-import rows with quantity 0 and no status wait for the user's wishlist/archived choice. Ingestion writes catalog rows only, never inventory (it used to wishlist every shade for the admin who ran the job; `POST /api/inventory-admin/imported-wishlist/backfill` removes those rows while untouched). Admins set a shade's category from `/polishes` (row "Accessory" action) or the detail page's "Catalog data" card, which also lists every vendor listing behind the shade with its raw and normalized JSON (`GET /api/shades-admin/{id}/source-products`). The `/polishes` ownership filters are a single `status=` URL list (`apps/web/src/lib/polish-list-url.ts`).

## Wear stats

**Wear stats:** `user_inventory_item.wear_count` and `last_worn_at` are derived from the mani log (`manicure` / `manicure_polish`, keyed by `shade_id`): `packages/functions/src/lib/manicure.ts` `recomputeWearStats()` rewrites them for the affected shades after every manicure create/edit/delete (and after polish create/update), never by incrementing or decrementing. `tried_at` is only filled from the earliest wear when NULL, never cleared by the log.

## Collection stats

**Collection stats:** `GET /api/stats/collection` (`packages/functions/src/lib/collection-stats.ts`) aggregates the caller's inventory in six `user_id`-scoped SQL queries, plus the wishlist value (`wishlist: { count, listPrices }`: the wishlist's buy-link list prices summed per currency server-side, so the web dashboard and the `/polishes` Wishlist header never page through every wishlist row). Money is grouped by `purchase_currency` and never summed across currencies (`null` currency is its own group); spend counts `owned`/`destash`/`archived` rows with a price, and the month bucket falls back from `purchase_date` to the UTC `created_at` date. Cached per user for 60s in Redis; `invalidatePolishCachesForUser()` (`lib/polish-cache.ts`) drops the entry, so any new inventory or mani-log write path must call it.

## Wishlist value

**Wishlist value:** `sumListPrices` in `packages/shared/src/money/price-totals.ts` (decimal-safe, per currency, unpriced rows counted never guessed; the Looks shopping list uses it too) totals every wishlisted row's list price for the web `/polishes` Wishlist header (`WishlistValue`) and dashboard Wishlist tile and the mobile Wishlist preset header and Insights Wishlist panel, from a dedicated fetch of all wishlist rows (not the visible page; mobile caches the slim price fields per user as `wishlist-value`).
