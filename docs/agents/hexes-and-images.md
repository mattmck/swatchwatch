# Shade hexes and catalog images

Covers vendor / detected / name hexes with provenance, the snap step, hex labeling and promotion (D12), catalog thumbnails and catalog galleries (dedupe, download cap).

## Shade hexes

**Shade hexes:** each shade has `vendor_hex` (vendor product data), `detected_hex` (AI vision on the product image) and `name_hex` (from the color name). Every `detected_hex` write also records provenance (`detected_hex_confidence`, `detected_hex_method`, `detected_hex_model`, `detected_hex_prompt_version`, `detected_hex_at`; migration 20261017024958000_shade-detected-hex-provenance) via `packages/functions/src/lib/hex-provenance.ts`, and `shade.hex_agreement` is a generated column holding the OKLAB distance vendor ↔ detected. Bump `PROMPT_VERSION` in `ai-color-detection.ts` whenever the vision prompt changes.

**Snap step (behind `HEX_DETECTION_SNAP_ENABLED`, default off):** every `detected_hex` write path (ingestion sync detection, the batch-submit fallback, the batch poller apply step and admin `recalc-hex`) runs `snapDetectionToImage` from `packages/functions/src/lib/hex-snap.ts` after `detectHexWithAzureOpenAI`: it re-reads the *same image the model was shown* (`lib/detection-image.ts`: data URI, `/api/images/{id}` proxy id decoded to its blob, or the vendor URL; the poller takes each row's image from the batch input file) and replaces the model's hex with the nearest palette chip measured from it (`extractPaletteCandidates`) when one is within `HEX_SNAP_MAX_DISTANCE` (default 0.10). Snapped rows are stored with `detected_hex_method = 'vision-snap'`; a detection with no chip close enough, or whose image cannot be read, keeps the raw hex and `vision-direct`. The prompt and `PROMPT_VERSION` do not change. The eval `blind-snap` strategy imports the same module. Display uses `resolveDisplayHex` (vendor > detected > name); `resolveDisplayHexDetailed` in `packages/shared` adds the source, agreement and a review flag (disagreement > 0.10 MEDIUM, or a caller-marked suspicious vendor hex). Admins review weak detections with `GET /api/polishes-admin/hex-review`, and build hand-picked ground truth for the hex-detection eval in the admin console's Hex Labeling tab (canvas eyedropper over a shade's catalog images → `color_training_sample` rows with `source_type = 'manual'`, one per shade, via `/api/hex-labels-admin/*`; migration 20261017170047543_hex-ground-truth-labels). Saving a label never writes `vendor_hex`/`detected_hex`.

**Promote to vendor hex (#321, D12):** the only exception is the explicit, confirmed per-label admin action `POST /api/hex-labels-admin/labels/{id}/promote` (`lib/vendor-hex.ts`; approved labels only, never private `user_submitted` shades), which copies the label's hex to `vendor_hex` with provenance (`vendor_hex_source` `vendor | manual_label`, `vendor_hex_label_id`, `vendor_hex_set_by_user_id`, `vendor_hex_set_at`, `vendor_hex_previous`; migration 20261020024540860_shade-vendor-hex-provenance) and an `admin_audit_event` row in the same transaction; Undo (`DELETE …/labels/{id}/promote` or `DELETE …/shades/{shadeId}/promotion`) restores `vendor_hex_previous`. Deleting a promoted label keeps the hex (FK ON DELETE SET NULL).

**D12 ingestion rule:** every connector `vendor_hex` write goes through `planIngestedVendorHex` on a `FOR UPDATE` read and never replaces a `manual_label` hex; the incoming vendor value goes to `vendor_hex_previous` so Undo restores current vendor data. The provenance is admin-only (not in user-facing polish responses); display still uses vendor > detected > name. `eval:hex:populate` exports labels as `manual` cases scored on the sampled image (which needs a public vendor URL from `source_image_url`). Canvas reads rely on `/api/images/{id}` CORS: allowed origins get `Access-Control-Allow-Origin`, every image response has `Vary: Origin`, and private `v3` responses never get `*`.

## Catalog thumbnails

**Catalog thumbnails:** ingestion (`uploadSourceImageToBlob` → `ensureImageVariants`) writes pre-generated square WebP thumbnails next to each catalog blob, `<blob>.c<IMAGE_VARIANT_CROP_VERSION>.w<size>.webp` for `IMAGE_VARIANT_SIZES` (64/128/256/512, `packages/shared/src/constants/image-variants.ts`). Studio shots on a flat background are cropped to a square around the product (trim the background, `planImageVariantCrop` in `packages/functions/src/lib/image-variants.ts`); other photos are center-cropped. Bump `IMAGE_VARIANT_CROP_VERSION` whenever the crop or rendering changes (variant blobs are never rewritten) and run the backfill. The image proxy snaps public `?w=n&h=n&fit=cover&fm=webp` requests up to that ladder and serves the variant blob, falling back to rendering it from the original (same `renderImageVariant`) when it is missing; private `v3` media has no variants. The web renders catalog thumbnails with `SwatchThumbnail` (`buildSwatchThumbnailSources`: 1x/2x `srcSet`). Changing the ladder needs a backfill (`POST /api/images-admin/variants/backfill`, looped by `npm run backfill:image-variants`).

## Catalog galleries

**Catalog galleries:** a shade's catalog images are its `swatch` rows (`source_product` = primary, `source_gallery` = additional) over `image_asset` rows deduped by `(owner_id = data source, checksum_sha256)`. After linking a product's images, ingestion makes the shade's `source_gallery` swatches from that data source exactly the product's current images (`pruneStaleGallerySwatches` in `packages/functions/src/lib/gallery-dedupe.ts`; only when every image was stored this run, skipped when another product of the same source maps to the shade; `source_product`, other sources, user media, and swatches whose image has a `color_training_sample` label or that have `color_features` are never touched; `image_asset` rows and blobs are kept). Existing duplicates (the same picture stored twice under different checksums by older ingests) are removed by the admin perceptual-match cleanup `POST /api/images-admin/gallery-dedupe` / `npm run dedupe:gallery-images`. Each `image_asset` row stores a perceptual fingerprint (`perceptual_hash`, `thumb_fingerprint`, `image_width`, `image_height`, all-or-nothing; migration 20261018234237112_image-asset-perceptual-fingerprint), computed by `uploadSourceImageToBlob` from the stored bytes and backfilled by the cleanup endpoint for images reused by URL without a download. Ingestion does not link an additional image as a `source_gallery` swatch when it near-duplicates an image already linked for the product in that run (`planProductGalleryLinks`, `INGEST_NEAR_DUPLICATE_THRESHOLDS`: dHash ≤ 64, thumbnail MAD ≤ 20, aspect ≤ 3%, measured on Cracked Polish: catches small same-aspect re-crops and same-pose re-shoots, not crops to another aspect) or the product already links `GALLERY_MAX_IMAGES_PER_SHADE` gallery images; skipped images are still stored and kept in the prune keep-set, a swatch an earlier run linked for one is unlinked (unless protected or the shade is shared with another product of the source), and the image AI hex detection chose (`chooseUploadedImageForDetection`, which still sees every upload) is always linked.

**Download cap:** before any download, `SOURCE_IMAGE_MAX_PER_PRODUCT` (default 8, clamped 1–50, no unlimited value; `planProductImageDownloads` in `lib/product-image-cap.ts`) picks which images are downloaded and stored: the primary, the image AI detection would choose (ranked from alt text / filename before download, kept even past the cap), then vendor order; an image past the cap whose URL is already stored is reused, the rest are not downloaded (`imagesSkippedByCap`). The prune's "every image stored" means every image this run kept or reused, so capped runs still prune and never unlink a still-listed stored image.
