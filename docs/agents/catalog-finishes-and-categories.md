# Catalog: finishes and product categories

Covers shade finishes (finish catalog, catalog write rule #224, finish families, product text) and product categories (#349, #347, D23).

## Finishes

**Finishes:** shades carry `shade.finishes text[]` (canonical, primary first) plus the legacy `shade.finish` (identity key, kept for backward compat). At runtime the admin-managed `finish_type` table is the source of truth for which finishes are valid, and `finish_normalization` holds the alias spellings; both are loaded together (one cached query) by `loadFinishCatalog()` in `packages/functions/src/lib/finishes.ts`, so a finish type created only in the admin UI is fully usable (parsing, validation, filtering, form options). `CANONICAL_FINISHES` in `packages/shared` holds the built-in seeded defaults, used for typing (`PolishFinish`) and as the fallback when the DB/reference API is unavailable; a test keeps it equal to the migration seeds. Request `tags` on polish create/update never modify catalog finishes (shades are shared); only ingestion connectors parse finishes from product tags.

**Catalog write rule (#224):** user-supplied `finishes`/`finish` and color fields (`color`, `vendorHex`, `detectedHex`, `nameHex`) are written to a shade only when the request creates it; adopting, matching or updating an existing shared shade never changes them (not even to fill an empty value), except that a user may keep correcting their own private `user_submitted` shade; a `PUT /api/polishes/{id}` with a new brand/name on that shade renames the row in place (same `shade_id`, so inventory, mani log and events stay attached), and a brand + name another visible shade already has answers 409 `shade_identity_taken` with `existingShadeId` (`ShadeIdentityTakenResponse`) and changes nothing. A `finish_type` still used by any shade (`shade.finishes` or legacy `shade.finish`) or `finish_normalization` alias cannot be deleted: `DELETE /api/reference-admin/finishes/{id}` returns 409 with the usage counts (`FinishTypeInUseResponse`). Renaming one (`PUT` with a new `name`) cascades in one transaction: `finish_type.name` and the `finish_normalization` rows pointing at it change in a single statement (non-deferrable FK), `shade.finishes`/`detected_finishes` entries are rewritten, and an alias old → new name is added; the legacy `shade.finish` is never rewritten because it is the raw vendor dedup key. A name another type already has (any case) returns 409 `FinishTypeNameTakenResponse`. AI prompts (vision hex/finish detection, sync and batch, label OCR, and the eval palette-pick and region-crop prompts) list the finishes from `finishNamesForPrompt(loadFinishCatalog())`, falling back to `CANONICAL_FINISHES`.

**Finish families (#320, D10):** each `finish_type` has an optional `family` (`FINISH_FAMILIES` in `packages/shared`: solid, shimmer, holo, glitter, matte, thermal, glow; CHECK-constrained, migration 20261018175839000_finish-type-family seeds the built-ins), editable in the admin Configuration tab. `loadFinishCatalog()` returns it as `families` (`buildFinishFamilyMap`, catalog rows over the static `DUPE_FINISH_FAMILIES` fallback, which a test keeps equal to the seeds), and the dupe endpoints and the web's client-side add-guard check grade with it; a finish without a family still grades `unknown` and is never penalized. The API always sends `family` (`null` = none); a payload without the key keeps the built-in family.

**Product text (#352):** every connector also stores `descriptionText` and `descriptors` in `external_product.normalized_json` (`lib/product-text.ts`; no shade column, reached via `shade_source_product`, never in user-facing responses). Ingestion resolves finishes by precedence in `lib/finish-text.ts`: tags win, then descriptors, then description text (catalog names + aliases with negation/cross-sell/brand guards); text-derived finishes only fill a shade that has none. The vision prompt gets the text as a labeled vendor hint (`PROMPT_VERSION` `vision-direct/2026-10-v3`).

## Product categories

**Product categories (#349, #347; decision D23, plan `docs/plan-catalog-hygiene.md`):** `shade.product_category` (`color | topper | top_coat | base_coat | treatment | accessory`, default `color`; `PRODUCT_CATEGORIES` / `ProductCategory` in `packages/shared`, a test keeps the migration CHECK equal) plus `product_category_source` (`rule | admin`; migration 20261022190729000_shade-product-category). `classifyProductCategory` in `packages/functions/src/lib/product-category.ts` mirrors `docs/queries/catalog-hygiene-audit.sql` rule for rule (accessory from name/color name/title/product type or an explicit tool type tag, never free tags, with ambiguous words such as jewels/foils/studs counting only under a non-polish product type and a non-polish "Nail Art" product type counting too; multi-polish sets and bundles are `accessory` too, evidence `set`, never expanded into their polishes: set words in the name/title/type (bundle, duo, trio, quad, gift/box/mani set, advent calendar, countdown box, full collection, "3 pack"; ignored after Dam's "… Nail Polish - <release>" notes), a name/title/type without " - " parts that ends in set(s)/collection, or a whole set tag such as `bundles-sets`/`collection-set`; topper beats coat wording; then base coat, top coat, treatment, read from the name/title/product type before the tags; else color): change the audit query first, then the classifier. Every connector gates products with `classifyIngestedProduct` (accessories, sets (even when a Shopify store filter keeps them) and the June tag blocklist skipped; coats/treatments ingested with their category) and materialization writes the rule category, never over an `admin` one. Vision hex detection (sync, batch, recalc-hex) runs on `color` only. The admin backfill `POST /api/shades-admin/product-category/backfill` (dry run by default; `npm run backfill:product-category`) re-classifies the catalog, sets `status = 'excluded'` on accessories nobody holds (held ones are listed), and with `clearTopperDetectedHex` clears suspicious topper `detected_hex` values; every change is logged in `shade_category_change` (before/after, run id) so it can be undone. Admin override: `PUT /api/shades-admin/{id}/product-category` (sticky). Surfaces (D-C): accessories and `excluded` shades are visible only to holders (`POLISH_VISIBLE_SQL`, import matching) and never in catalog search; color search, gaps, photo match, hex review/labeling are color-only; dupes compare color↔color and topper↔topper only (`areDupeComparableCategories` in the shared dupe rule); Pick for me never picks a non-color main polish (pair-it may add a topper); stats count coats/treatments in spend only and drop accessories; the mani log prefills roles from the category (`manicureRoleForCategory`). `?category=` filters `GET /api/polishes` and catalog search; responses and the export carry `productCategory`.
