# Auth, telemetry and backups

Covers authentication (Entra External ID, web token renewal, admin user management, sign-in methods), telemetry and alerts, and backups.

## Auth

**Auth:** Azure AD B2C / Entra External ID (tenants and the web app registration provisioned outside Terraform via portal; only the web app's service principal can be Terraform-managed, opt-in per environment with `manage_ciam_service_principal`, through the `azuread.ciam` provider and a GitHub-OIDC deployer app in the CIAM tenant — see `infrastructure/README.md`). Functions read `AZURE_AD_B2C_TENANT` and `AZURE_AD_B2C_CLIENT_ID` from environment. Token validation is JWT-based via the `/api/auth/validate` endpoint.

**Web token renewal:** every API call gets its token from MSAL `acquireTokenSilent` (renewed within 5 min of expiry; `getFreshAccessToken()` in `apps/web/src/lib/auth-token.ts`), and any silent failure redirects to sign-in (30 s loop guard, `lib/token-renewal.ts`), except a network failure (browser offline, MSAL/fetch network error; `isOfflineRenewalFailure` in `lib/offline.ts`), which keeps the user on the page so saved copies open read-only (`isAuthOffline()` lets `RequireAuth` through) and renews on the `online` event or the next API call. Hidden-iframe renewal uses `/blank.html` (MSAL v5 redirect bridge, script copied from `@azure/msal-browser` before dev/build), which must be an SPA redirect URI on the Entra app registration for every web origin. `app_user.role` is re-synced from the token's Entra `roles` claim on every sign-in, so admin is granted in Entra (app role `admin`), never edited in the app.

**Admin user management (#45):** `/api/users-admin*` (`admin-users.ts`, `lib/admin-users.ts`; migration 20261018180032156_admin-user-management) lists/searches users, edits the handle and suspends/reactivates accounts; a suspended account (`app_user.suspended_at`) gets 403 `account_suspended` from `withAuth`/`withAdmin` (read via `to_jsonb(app_user.*)` so auth survives an un-migrated DB), an admin cannot suspend themselves, and every change and account merge writes an `admin_audit_event` row (who, what as before/after, when, target) in the same transaction.

**Sign-in methods / password reset (#45, `docs/admin-password-reset.md`):** each environment has one External ID tenant (email + password, Google, Facebook); one email address is one Entra user with exactly one sign-in method (Entra sends a second sign-up with the same address to the existing method), and SwatchWatch stores no passwords. Reset is never done by the app: email + password users use "Forgot password?" on the Microsoft sign-in page, Google/Facebook users reset with that provider, and admins get copyable instructions plus an Entra admin center link per identity in `UserDetailDialog` (`apps/web/src/lib/entra-admin-links.ts`; Entra logs admin resets in its own audit log). Suspend is the lockout tool.

## Telemetry

**Telemetry:** Functions and web both report to the same workspace-based Application Insights (see `docs/observability-plan.md`). The web SDK is lazy-loaded after hydration, sends W3C `traceparent` only to the API host, tags telemetry with the internal user id (never email), and redacts `/api/images/{id}` capability ids and shared wishlist/look tokens; route-group `error.tsx` files and `app/global-error.tsx` report render errors. M2 success metrics (D19): browser events `dupe.warning_shown` / `dupe.warning_outcome` / `mani.logged` / `import.completed` / `onboarding.step_clicked` from `apps/web/src/lib/metrics-events.ts`, plus the weekly read-only query `docs/queries/m2-metrics.sql`. Prod alerts (Terraform, `alerts_enabled`) email `alert_email` on API 5xx, exception spikes (server + browser), `ingestion.job_failed` events (emitted by `markIngestionJobFailed`), the daily cap being hit, and failing availability tests (web home page, `GET /api/reference/finishes`).

## Backups

**Backups:** all in Terraform (`infrastructure/main.tf`, see `infrastructure/README.md` → Backups & Restore), nothing geo-redundant. Postgres has 35 days of point-in-time restore. The app storage account has blob versioning, change feed and blob + container soft delete, with a management policy that expires old versions. That account also holds the live Terraform state in its `tfstate` container, so never remove that container. In prod (`backup_vault_enabled`) an Azure Backup vault takes weekly Postgres and daily `nail-photos` backups, and `CanNotDelete` locks cover Postgres, the storage account and the vault (`delete_locks_enabled`). Key Vault has purge protection. The vault role assignments and the locks need User Access Administrator, so the first apply that adds them runs locally, not in CI.
