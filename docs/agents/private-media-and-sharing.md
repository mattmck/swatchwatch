# Private media and sharing

Covers private user media (`v3` image-proxy URLs, orphan sweep, capture frames) and the opt-in shareable wishlist and shareable looks pages.

## Private media

**Private media:** user photos (today the per-item nail photo, #270) live in `USER_MEDIA_CONTAINER`, referenced by `image_asset` rows with `owner_type = 'user'`, and are only ever exposed as owner-scoped `v3` image proxy URLs that require the owner's bearer token (web: `PrivateImage`). The mobile app (`apps/mobile`: nail photo on polish detail, mani photos) fetches `v3` URLs only with the bearer token and only from the API origin, keeps the bytes as in-memory data URIs (`expo-image` `cachePolicy="none"`, never a disk cache or AsyncStorage) and clears them on sign-out (`src/lib/private-image-loader.ts`). Every upload is re-encoded server-side so no EXIF/GPS metadata is stored; never return raw blob URLs or public `v2` ids for user media. Admin bottle-eval frames also live in `USER_MEDIA_CONTAINER`, under `{adminUserId}/bottle-eval/{sampleId}/`, as `owner_type = 'user'` `image_asset` rows linked by the `bottle_eval_frame.image_id` foreign key (so the orphan sweep never deletes them), served only as owner-scoped `v3` thumbnails; deleting a sample removes the blobs under the frame owner's prefix (not the caller's). Rows orphaned by cascade deletes outside the API (an `app_user` delete, an admin merge removing a duplicate inventory row) are removed by the daily `orphan-media-sweep` timer (#319, `src/lib/orphan-media-sweep.ts`): an `owner_type = 'user'` asset whose `captured_at` is older than `ORPHAN_MEDIA_SWEEP_GRACE_SECONDS` (rows without `captured_at` are never swept) that no foreign key references (discovered from `pg_constraint` each run, so new referencing tables are covered automatically) loses its blob first, then its row; only blobs in `USER_MEDIA_CONTAINER` under the owner's `{ownerId}/` prefix, and used by no other `image_asset` row, are ever deleted.

**Capture frames:** while `BOTTLE_CAPTURE_ENABLED` is on, the EXIF-stripped bytes of a Rapid Add data-URL frame are kept as a private blob under `{userId}/capture/{captureId}/{sha256}-{uploadId}.{ext}` (a fresh id per upload, so a retried frame never shares a blob; `src/lib/capture-frame-store.ts`; `image_asset.storage_url` is the blob URL, never a `v3` id, never in a response; flag off keeps the `inline://capture/…` placeholder). A session reaching `matched`/`unmatched` (finalize, answer) deletes its blobs and resets the rows to the placeholder, and the hourly `capture-frame-sweep` timer does the same for frames older than `CAPTURE_FRAME_RETENTION_SECONDS` (24 h); only blobs under the owner's `{ownerId}/capture/` prefix are ever deleted or reset (nail photos a frame references by `imageId`, mani photos, bottle-eval frames stay), an asset that is also a mani or nail photo or another frame's image is never released, a capture frame cannot be attached as a mani photo (400), and `quality_json` is never touched.

## Shareable wishlist

**Shareable wishlist (#268):** an opt-in, revocable public read-only page for a user's `status = 'wishlist'` items, entirely behind the server flag `SHAREABLE_WISHLIST_ENABLED` (default off, pending roadmap §6 decision 2; all `/api/wishlist-share*` and `/api/wishlist/{token}` routes 404 with `code: "feature_disabled"` while off, and the web card hides itself on that response). One `wishlist_share` row per user (migration 20261017064751368_wishlist-share) stores only a salt and `SHA-256(token)`; the token is `HMAC(subkey of IMAGE_PROXY_SIGNING_KEY, user_id:salt)`, re-derivable by the owner but not from a DB leak. The public payload is an explicit allowlist (owner-chosen display name; brand, shade, finishes, display hex, public `v2` catalog image) — never ids, email, notes, prices, quantities, private `v3` media, or the owner's private `user_submitted` shades. Anonymous reads are rate-limited per IP and per token with in-memory token buckets (`src/lib/rate-limit.ts`, best effort per instance).

## Shareable looks

**Shareable looks:** the same pattern for one saved look (`user_look`): an opt-in, revocable public read-only page at `/l/?token=…`, entirely behind the server flag `SHAREABLE_LOOKS_ENABLED` (default off in every environment; `/api/look-share` and `/api/look/{token}` 404 with `code: "feature_disabled"` while off, and the Looks page hides its Share link controls). One `look_share` row per saved look (migration 20261023001607416_look-share; composite FK `(user_look_id, user_id)` pins it to the look's owner, and deleting the look deletes the link) stores a salt, `SHA-256(token)`, a per-link display name and `revoked_at`; the token is `HMAC("look-share:v1" subkey of IMAGE_PROXY_SIGNING_KEY, user_id:user_look_id:salt)`, a different subkey from the wishlist's. Revoking keeps the row so the old link answers 410 `share_revoked`; sharing again mints a new token. The public payload (`toPublicLook` in `packages/functions/src/lib/look-share.ts`) is an allowlist: display name, template id, vibe (occasion/mood/finish), and per step the role and hex, plus brand, shade, finishes and a public `v2` catalog image only when the step's shade is a public catalog shade (`status = 'active'`, not an accessory, not merged); every other step is a plain color chip. Never ids, email, ownership (owned vs to buy, "owned only"), notes, prices, the saved snapshot's free text, or private `v3` media; the page names the look and steps from the built-in templates and derives application order and finish notes from the payload. Anonymous reads are rate-limited per IP and per token like the wishlist (separate buckets).
