# Ingestion: sources, connectors and buy links

Covers the MakeupAPI cleanup, brand-store self-correction, buy-from-brand links and list prices, source kinds and retailer listings (fill-only writes, listing freshness), retailer mode and the brand sources connectors (Shopify, product feeds, sitemap + JSON-LD, WooCommerce, Big Cartel).

## MakeupAPI and brand-store correction

**MakeupAPI (disabled; migration 20261026045216957_makeupapi-cleanup):** the `MakeupAPI` data source is frozen 2015 data (dead well.ca / dior.com / cloudfront URLs, scraped hexes), so it is disabled. Its materializer keys a variant on brand + color name, never the product name (Dior lists a family's sibling colors on every product), compared with the dedupe's `makeupApiNameKey` (codes stripped, `MAKEUPAPI_CODE_SUFFIX_PATTERN` shared with the SQL) against names and aliases, follows `merged_into_shade_id`, links only to a single same-category candidate (several = skipped), and writes catalog data only to shades it creates; an existing shade (store, seed, merge survivor) only gains the MakeupAPI `shade_source_product` listing. `POST /api/shades-admin/makeupapi-dedupe/backfill` (`lib/makeupapi-dedupe.ts`, `npm run dedupe:makeupapi-shades`, Backfills tab "MakeupAPI duplicates"; dry run by default) merges MakeupAPI-only shades (listings all MakeupAPI, `collection` = one of those product names) into the brand's one active non-MakeupAPI shade with the same name after stripping trailing "(40052)"-style codes, or folds MakeupAPI copies into the most-held copy, through `mergeShadeInto` with `sourceKind: "catalog"` (retired row `excluded` + `merged`; every listing and learned barcode moves, the survivor's catalog data never changes), then deletes MakeupAPI-only shades nothing references (any FK to `shade` from `pg_constraint` other than aliases / listings / the category log, an admin edit, or a user-created / review-approved shade keeps one), writing `admin_audit_event` `shade.catalog_merge` / `shade.catalog_delete` rows.

**Brand-store re-runs self-correct (`lib/brand-store-correction.ts`):** a `brand`-kind record whose shade was found through its own listing moves that shade to the record's resolved brand and clean title-parser name when an earlier run filed it under a vendor spelling or raw title (case-only renames included; SKUs follow; old name and raw title kept as aliases), or merges it through `mergeShadeInto` (`sourceKind: "catalog"`) into the brand's one same-name shade a fresh run would have found (exact identity, else one adoptable retailer shade, which the brand store then takes over per D26); it never touches a user's / approved / admin-edited shade or one another brand-kind source lists, and skips (logs) several or non-identity same-name matches rather than making a second shade; each change is a job-log line, `brandStoreShades*` job metrics and an `admin_audit_event` (`shade.catalog_correct`, migration 20261110150000000, or `shade.catalog_merge`) for the admin who queued the job. Shades whose every listing the store's current gate now rejects (gel while `includeGel` is off, another vendor's items) are excluded by `POST /api/shades-admin/brand-store-rejected/backfill` (`lib/brand-store-rejected.ts`, `npm run backfill:brand-store-rejected`, dry run by default; re-gates the stored `raw_json`, held / protected shades kept, `shade_category_change` `exclude` rows); brands are never deleted.

## Buy from brand

**Buy from brand (#267):** polish list/detail and catalog search/shade responses carry an optional `buyUrl` — the brand product page from the connector-stored `external_product.normalized_json ->> 'productUrl'`, reached through `shade_source_product` (written by ingestion materialization; migration 20261017061344201_add-shade-source-product). `packages/functions/src/lib/buy-link.ts` validates (absolute http/https only, no credentials) and picks one product deterministically (products of a disabled `data_source` and listings marked missing are never used; then a listing not known to be sold out before a sold-out one, then a brand store before a feed before a retailer (`data_source.metadata.kind`, unset or unknown = brand), then latest `last_seen_at`, then latest `fetched_at`, then highest id; see Source kinds below). No affiliate parameters; `applyAffiliateParams()` is the one place to add them. The same chosen product's vendor list price rides along as optional `buyPrice` / `buyCurrency` / `buyPriceSeenAt` (`selectBuyFromBrandLink` returns `{ url, price?, currency?, priceSeenAt? }`; only when both a valid amount and an ISO 4217 currency are stored; `priceSeenAt` = `external_product.fetched_at`; never the user's `purchase_price`, never converted or summed across currencies). Connectors write `price` (decimal string) + `currency` into `normalized_json` via `lib/product-price.ts`: Shopify-style stores take the lowest available variant price (else the lowest variant) and the store currency from `data_source.metadata.currency`, else the shop's `/meta.json`, else null (USD is never assumed); MakeupAPI keeps its ISO `currency` only; OpenBeautyFacts has none. Older rows: `npm run backfill:product-price`. The web renders it via `BuyFromBrandLink` with `rel="noopener noreferrer nofollow"` (with the price and an "as of" hint on wishlist/catalog rows and the detail page, per-currency subtotals on the Looks shopping list); mobile shows the price under the detail screen's buy button.

## Source kinds, retailer listings and listing freshness

**Source kinds, retailer listings and listing freshness (Polish Pickup plan `docs/superpowers/plans/2026-11-06-polish-pickup-retailer-listings.md`, brand sources plan `docs/superpowers/plans/2026-11-08-brand-sources-ingestion.md`):** one key, `data_source.metadata.kind`: absent = a brand store (the authority for its own shades), `retailer` (a multi-brand shop) or `feed` (a product feed), read by `lib/source-settings.ts` (`readSourceSettings` / `readSourceKind` per job, where an unknown value throws and fails the job; `sourceKindFromMetadata` on read paths, unknown = brand; `sourceKindSql` / `isBrandSourceSql` in SQL), which also reads `imagesPermitted` (images stored and AI-detected only when true; default true for a brand source only; this is the permission, separate from the admin's operational switches `metadata.ingestion.downloadImages` / `detectHex` (`readIngestionSwitches`, on unless `false`), which `planSourceImageWork` ANDs with it: no image work when `downloadImages` is off, no AI hex detection when `detectHex` is off), `includeGel`, `vendorAliases`, `maxPages` and the connector keys.

**Shade lookup** (`findExistingShadeForRecord`, run before any image work by `preResolveRecordShades`, so an ambiguous record or a retailer/feed record on a shade showing another source's product image costs no upload or vision call): the product's single existing `shade_source_product` listing wins (any status, unmerged); several listings skip a retailer/feed record, and a brand record falls back to its exact identity match only when that shade is one of the linked ones, else it is skipped; then a brand store tries the exact identity (brand + name + legacy `finish` + `collection`, or the raw title), retailer/feed skip it; then same-name `active`/`excluded` shades of the brand (for a brand store only ones with no legacy finish and no collection that a retailer or feed created, `catalog_authority = 'retailer'`, and no brand listing points at yet, since a takeover flips the authority only once the brand's detected hex is in; when detection does not apply to the brand record (images off, non-color category, or no image) the flip happens immediately and the retailer's `detected_hex` stays until a brand run with `overwriteDetectedHex` replaces it), kept when their finish families fit; exactly one is adopted, none creates a shade, several skip the record (`ambiguousShadesSkipped` is only a count; each skipped product is a `Skipped record` warning in the job log carrying `candidateShadeIds`, and because the stored job log is bounded (`INGESTION_JOB_LOG_MAX_ENTRIES`, an omission marker stands in for the dropped middle) a long run's warnings are read from the Azure Functions logs, where `JobLogger` forwards every warning; `docs/queries/ambiguous-listings.sql` finds only products that older runs already linked to several shades, not the skips). The AI batch apply resolves the shade through the same single listing first (`applyAiBatchShadeDetections`). A shade a retailer or feed creates gets `catalog_authority = 'retailer'`. Polish Pickup (`PolishPickupShopify`, `source_type` `api`, USD, migration 20261106120000000_retailer-listings) runs through the generic Shopify connector with a store filter (`store-filters/polish-pickup.ts`: `PPU` kept, `Merchandise` / `Hand & Nail` / `Gift Cards` dropped, `IPU` and the rest deferred to the generic gate) and a title parser (`connectors/shopify-title.ts`, `SHOPIFY_STORE_TITLE_PARSERS`: `Vendor | Shade` and `<Type> by Vendor | Shade` give the shade name; its description's `Cap: N` and the release tag go to `normalized_json` only). It is registered disabled (`SHOPIFY_SOURCES_PENDING_APPROVAL`, `pendingApproval`) until the owner records the store's OK (`docs/indie-sources-2026-10.md`), and nothing schedules it: it is run by hand from Admin Jobs. What a listing may write is planned by `planListingWrites` (the one write-rule implementation): a retailer or feed never overwrites (`overwriteDetectedHex` is forced off), never replaces a `detected_hex` (AI detection runs only when the shade has none) or non-empty `detected_finishes`, and links images only to a shade with no product image or whose product image it supplied itself; on a shade it did not create whose `shade.catalog_authority` is `brand_store` it is strictly fill-only: it links itself (`shade_source_product`, buy link, price), never changes `product_category`, and fills `finishes` (`planIngestedFinishes`), `color_name`, `name_hex` only when empty; on a shade a retailer or feed created (`catalog_authority = 'retailer'`, migration default for old rows is `'brand_store'`) it otherwise writes like an owner (category, finish merge). The first brand-store listing that matches a retailer-created shade takes it over: it writes finishes (unless admin-set), category (unless admin-set) and `color_name` as if it had created the shade, replaces `detected_hex` with its own detection, and `catalog_authority` becomes `'brand_store'` for good, but `collection` is not rewritten, the flip waits until the brand's detected hex is written (sync) or is done by the batch apply step (`BATCH_OVERWRITE_SQL`), and the retailer's gallery swatches are unlinked (`unlinkRetailerGallerySwatches`, same protections as `pruneStaleGallerySwatches`) only when the brand linked its own primary and its gallery set is complete.

**Listing freshness:** on the first pull of a job that returns a `catalog` (a fresh Shopify download, a fresh feed download, or the pull that completes a sitemap crawl, which can be a continuation; partial crawl pulls never mark anything), `markExternalProductsMissing` (`lib/listing-freshness.ts`) sets `external_product.missing_since` on this source's rows absent from that catalog and clears it on those present, but only when the catalog is complete (`catalog.complete`: a Shopify fetch that ended on a short page) and non-empty, so a truncated download retires nothing; job metrics `listingsMarkedMissing` / `listingsCleared`.

**Buy-link order** (`selectBuyFromBrandUrl`): disabled source or `missing_since` dropped, then a listing with a buyable variant (`available !== false`) before a sold-out one, then brand store before feed before retailer (`SOURCE_KIND_RANK` / `sourceKindRankSql`, also the description-text order for the vision prompt and the product-text backfill), then latest `last_seen_at`, `fetched_at`, highest id. Availability comes from store variant data, never HTTP status.

**Names and brands:** every Shopify title loses one trailing ` PPU` / `(PPU)` token (`stripRetailerExclusiveSuffix`), so Cracked Polish's `Sniff Test PPU` and Polish Pickup's `Sniff Test` are one shade; an existing shade stored under its raw title is renamed in place on the next ingest and keeps the raw title as a `shade_alias` (`renameShadeToCleanName`); a vendor resolves to an existing brand by `name_canonical` or exact case-insensitive `brand_alias` (the migration seeds aliases for suffix-only differences, `Bee's Knees` -> `Bee's Knees Lacquer`). A retailer or feed listing adopts any same-name shade of the brand whose finish family fits (the shade lookup above), so a brand store that tags `finish:`/`collection:` (e.g. Mooncat, Holo Taco) is matched too; Polish Pickup stores no images unless its metadata gets `imagesPermitted: true` with the owner's OK. A brand-store takeover with detection off keeps the retailer's `detected_hex` (COALESCE) until an overwrite run. When the clean name matches one shade and the raw title ("X PPU") another, the job log warns with both shade ids so an admin can merge them (never automatic). Post-release order: migrate, run each brand store once, only then enable Polish Pickup (after the owner's OK); the first brand run re-detects `X PPU` shades once. `idx_external_product_live` (partial index on live listings) is for the planned "Where to buy" listing query; no query uses it yet. Auto-provisioned retailer rows get `kind: 'retailer'` (`SHOPIFY_RETAILER_SOURCES`), and migration 20261106130000000 repairs an existing row.

## Retailer mode

**Retailer mode (brand sources plan Phase B, `docs/superpowers/plans/2026-11-08-brand-sources-ingestion.md`):** a generic Shopify source whose `metadata.kind` is `retailer` (and that has no store title parser of its own, so Polish Pickup keeps `shopify-title.ts`) reads each listing through `gateRetailerListing`: the brand is the product's vendor mapped through `metadata.vendorAliases` (`resolveRetailerVendor`, keys matched lower-cased and whitespace-collapsed; a missing or placeholder vendor gives no brand and the product is skipped, because a multi-brand store's own name is never a polish brand), and the title is parsed by `parseRetailerTitle` (`lib/connectors/retailer-title.ts`, pure: `*PRE-ORDER*` dropped, the longest matching brand or raw-vendor prefix stripped, `#CODE` segments and glued codes read as the vendor code, sizes anywhere in a segment, trailing notes such as `(LE)` / `(Discontinued…)` / `(Magnetic)`, `Refill` and `Mini` dropped, product-line segments (`RETAILER_LINE_REGEX`) kept apart, a segment ending in a set word (`isRetailerSetSegment`) drops the listing, so a shade named "Jet Set" needs adding by hand or an alias). Retailer records carry `listingTitle`, `vendorCode` and `productLine` in `normalized_json` and empty `finishes` / `collections`, so a listing never sets the legacy `finish` identity key or a collection (canonical finishes only fill an empty shade under the retailer write rules above). After `recordShadeSourceProduct`, `recordRetailerAliases` adds the vendor code and the raw listing title as `shade_alias` rows (never one equal to the shade name), which typed catalog search and CSV import match, and the bottle resolver reads (non-code aliases as extra names, vendor codes by equality; the plain capture resolver does not). The three Phase B retailers (registered without `imagesPermitted`, so no images until the store's OK; Harlow & Co and Beyond Polish store images since 2026-11-10 by the owner's decision D28): Harlow & Co (`HarlowAndCoShopify`, CAD, migration 20261108120000000) and Beyond Polish (`BeyondPolishShopify`, USD, `includeGel: false`, `maxPages: 100`, migration 20261108130000000) are enabled; Hypnotic Polish (`HypnoticPolishShopify`, EUR, migration 20261108140000000) is disabled and pending the store's written OK. `SHOPIFY_RETAILER_SOURCES` in `shopify-generic.ts` must list every retailer (a test checks it against the seed's `"kind": "retailer"` rows), or auto-provisioning creates it as a brand store on a database without its migration. When a store asks us to stop using its pictures, an admin disables the source and runs the source image removal job (`POST /api/images-admin/source-images/remove`, `lib/source-image-removal.ts`, `npm run remove:source-images`, Backfills tab; disabled sources only, 409 otherwise, dry run by default, ~45 s batches): swatches, `image_asset` rows, blobs and thumbnail variants go, while hex-labeled / `color_features` images and blobs another row shares are kept. The duplicate audit is `docs/queries/retailer-duplicates.sql`.

## Brand sources

**Brand sources (plan 2026-11-08, PRs #502–#505 + Phase E; `docs/superpowers/plans/2026-11-08-brand-sources-ingestion.md`, evaluation `docs/brand-sources-evaluation-2026-11.md`, decision D26):** every source is a `data_source` row whose protocol (`SOURCE_PROTOCOL_MAP` in `lib/connectors/registry.ts`, `CONNECTOR_FACTORIES` in `ingestion.ts`) picks its connector, and every connector emits the same `ConnectorProductRecord` for the one materializer, so a new platform is a new connector and a new store kind is a connector option. Next to the older `HoloTaco` / `Shopify` (`products.json`), `OpenBeautyFacts` and `MakeupAPI` protocols, this batch adds four: `ProductFeed` (`metadata.feedUrl` or `base_url`, optional `metadata.feedAuthEnv`), `SitemapJsonLd` (`metadata.sitemapUrl`, `metadata.productUrlPrefixes`), `WooCommerce` (`base_url`, optional `metadata.brand`) and `BigCartel` (`metadata.subdomain`, required `metadata.brand`). Per-source behaviour lives in `data_source.metadata`, read once per job by `readSourceSettings`: `kind` (absent = brand store, `retailer`, `feed`; see Source kinds above), `imagesPermitted` (images stored and AI-detected only when true; default true for a brand store only, so retailers and feeds store no images until the store's written OK says images), `includeGel` (gel lines are out of scope by default, D26: the Beyond Polish, Londontown, Manucurist, Olive & June and CND store filters drop them unless it is `true`, and no source sets it to `true`), `vendorAliases` (vendor spellings → brand, in brand mode too: wet n wild, Olive & June, Barry M), `maxPages`, `currency` and `brand`. The buy link prefers a brand store over a feed over a retailer listing (`SOURCE_KIND_RANK`). Registration (each row in `docs/seed_data_sources.sql` plus a migration): Phase B (PR #503) the retailers Harlow & Co and Beyond Polish (enabled; images on since D28, 2026-11-10) and Hypnotic Polish (pending); Phase C (PR #504) 33 brand Shopify stores, the ten whose terms carry no automated-access clause enabled (Deborah Lippmann, Londontown, Côte, Manucurist, Olive & June, Piggy Paint (its SOPHi line stays its own brand), wet n wild, Alchemy Lacquers, Penelope Luz, Noodles), Mavala, CND and Barry M pending until their terms are read, and the 20 clause stores (Dazzle Dry … Modelones, Dreamland, Ethereal) pending, with store filters and title parsers where the probe showed empty or non-polish product types; Phase D (PR #505) the Polish Pickup fixture check and the maker roster script `roster:polish-pickup`; Phase E the nine non-Shopify rows below, all pending or blocked. A pending Shopify store is in `SHOPIFY_SOURCES_PENDING_APPROVAL` (`shopify-generic.ts`, which also auto-provisions it disabled), a pending non-Shopify source in `CONNECTOR_SOURCES_PENDING_APPROVAL` (`registry.ts`, bookkeeping: those are registered only by migration); both are seeded `enabled = false` with `"pendingApproval": true`; permission is recorded in the admin Sources tab (`/admin?tab=sources`), which stores it in `data_source.metadata.permission`; Record OK on a source not yet granted turns the store on (removing `pendingApproval`, setting `imagesPermitted`, appending the OK to `metadata.notes`) (re-recording an OK on a granted source only updates the record and images, never turns it on; No OK needed records a checked-terms status instead; open-data sources derive it) and audits the change in `admin_audit_event`, so enabling a store needs no code or migration (README "Enabling a pending store"). The same tab keeps one `brand_ingest_profile` per brand (website, platform, blocker, own store, matched explicitly, by `metadata.brand` or by the store's display name, never by listings); a brand added there before any shade exists is resolvable by the bottle flow but appears in no user-facing list. The run endpoints (`POST /api/ingestion/jobs`, `/api/ingestion/bulk`, `lib/ingestion-run-guard.ts`) answer 409 `source_blocked` for a row with `metadata.blocked` (even when enabled) and 409 `source_disabled` for a disabled row (pending or switched off), and the worker stops a queued job for such a source at start. When a store asks us to stop using its pictures, the source image removal job (see Retailer mode) removes a disabled source's catalog images.

**Google product feeds:** `<Brand>Feed` sources (`ProductFeed` protocol) are read by `ProductFeedConnector` (`lib/connectors/product-feed.ts`: Google Merchant Center XML (RSS/Atom, `g:` namespace) or TSV/CSV, URL from `base_url` or `metadata.feedUrl`, optional basic auth from the app setting `metadata.feedAuthEnv` names (`PRODUCT_FEED_AUTH_*` only, `https://` feed URLs only), one cached download windowed per page whose downloading pull reports the complete `catalog` for listing freshness; `feed`/`retailer` kinds parse titles with `parseRetailerTitle`, a `brand` source with `parseBrandStoreTitle`, which splits off a first segment only when it is the brand, the raw vendor or starts with a product-line word, so "Night Swim - Holo" stays whole; `parseConnectorTitle` picks one in all four new connectors); every non-Shopify connector writes `normalized.available: boolean | null` (the availability contract), which `BUY_LINK_CANDIDATES_SQL` reads before the Shopify variants, and Shopify-only code paths check the protocol (`isShopifyProductsSource` in `lib/connectors/registry.ts`), never a `…Shopify` name suffix; only Shopify sources are auto-provisioned, all others are registered by migration.

**Sitemap + JSON-LD:** `<Brand>Sitemap` sources (`SitemapJsonLd`) are read by `SitemapJsonLdConnector` (`lib/connectors/sitemap-jsonld.ts`: `metadata.sitemapUrl` (an index followed one level) and `metadata.productUrlPrefixes`, the first JSON-LD `Product` per page); the crawl is checkpointed in the job's catalog cache (`loadCheckpoint` / `saveCheckpoint`, fenced on the blob ETag; it needs a `durable` cache, i.e. `CONNECTOR_RAW_CONTAINER` and a successful preflight probe write, made lazily on the first `loadCheckpoint()`) and bounded by the worker deadline (`deadlineMs`, `SITEMAP_JSONLD_SAVE_MARGIN_MS`, 1 s pacing, `SITEMAP_JSONLD_MAX_PAGES_PER_RUN`). A page whose retries run out, that stays unanswered in 3 pulls, or whose fetch throws in 3 pulls (at once for an invalid URL) is recorded as `failed`, logged once through the pull's `log` when recorded, and skipped (it never blocks completion, keeps its listing, while a 404/410 page is left out of the catalog ids); robots.txt is read once per crawling pull and checked before every sitemap and page request (a disallowed page is left out like a 404, a disallowed child sitemap is skipped; `lib/robots.ts` matches `*` / `$` with an iterative glob, never a RegExp from remote text); only sitemap requests are fatal, and a fatal error saves the pull's progress before it is rethrown; a pull returning `metadata.catalogComplete: false` has no records and the worker pulls the same page again (ownership checked after every pull, hand-off by `crawlPullEstimateMs`, `checkpoint superseded` stops like lost ownership), and listing freshness runs once per job on the first pull that reports a complete catalog. `OpiSitemap` is registered disabled and pending (`CONNECTOR_SOURCES_PENDING_APPROVAL`).

**WooCommerce Store API:** a `<Brand>WooCommerce` source (`lib/connectors/woocommerce-store.ts`) pages `{base_url}/wp-json/wc/store/v1/products?per_page=100` (1 s apart, until a short page or `metadata.maxPages` / `SHOPIFY_CONNECTOR_MAX_PAGES`, cached per job, `catalog` complete only when the last page was reached), reads `metadata.brand` (else `brands[0]` or the "Brand" attribute), `currency` and `kind`, has no GTIN, converts `prices.price` from minor units, and is gated like Shopify (store filters keyed by source name over the platform-neutral `StoreFilterProduct`). Robots rule: each download reads `{base}/robots.txt` once before any product request and throws `WooCommerce Store API disallowed by robots.txt` when our `SwatchWatch` group, else the `*` group, has a `Disallow` prefix of the Store API path (`lib/robots.ts`; `Allow` is not read, a 4xx robots.txt allows). `PicturePolishWooCommerce` is registered disabled and pending; `IlnpWooCommerce` and `KbshimmerWooCommerce` are disabled with `metadata.blocked` `robots` / `cloudflare` (known-blocked, reached through resellers).

**Big Cartel:** a `<Brand>BigCartel` source (`lib/connectors/big-cartel.ts`) reads Big Cartel's read-only v0 API, one `GET https://api.bigcartel.com/{metadata.subdomain}/products.json` (no pagination) and `store.json` once 1 s later for the store URL (relative product `url`s resolve against it, else `base_url`, else `https://{subdomain}.bigcartel.com`) and `currency.code` (`metadata.currency` overrides); `metadata.brand` is required (the factory throws `BigCartel source <name> has no metadata.brand`, never the Holo Taco fallback); record `externalId` = permalink, `gtin` null, `available` = `status === "active"` (a sold-out product is kept), images `secure_url`, price `default_price`; gated like WooCommerce, and both gates reject a mystery / grab-bag title first (`MYSTERY_TITLE_REGEX` in `store-filters/shared.ts`) because a store category can carry a polish signal. `PaintedPolishBigCartel`, `PotionPolishBigCartel` (replaces the disabled `PotionPolishShopify`, whose notes say it is superseded), `ColoresDeCarolBigCartel`, `GlistenAndGlowBigCartel` and `PoetryCowgirlBigCartel` are registered disabled and pending (migration 20261108190000000_add-big-cartel-sources) until the owner reads Big Cartel's API License Agreement and each store's terms.
