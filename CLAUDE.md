# SwatchWatch — Agent Instructions

## Architecture Overview

Smart nail polish collection manager. **npm workspaces monorepo** with three deployable targets and a shared types package:

```
apps/web          → Next.js 16 (App Router) + Tailwind v4 + shadcn/ui → Azure Static Web App
apps/mobile       → Expo / React Native (SDK 57, RN 0.86) + Expo Router
packages/functions → Azure Functions v4 (Node 22, TS)    → Azure Linux Function App
packages/shared    → Shared TypeScript types (polish, user, voice)
infrastructure/    → Terraform (azurerm ~4.50) for all Azure resources
```

**Data flow:** Clients → Azure Functions REST API (`/api/polishes`, `/api/polish-imports`, `/api/auth/*`, `/api/voice`) → Azure Database for PostgreSQL Flexible Server (schema in `docs/schema.sql`). Voice input goes through Azure Speech Services → Azure OpenAI for parsing polish details from transcriptions. Full canonical schema uses `pg_trgm` for fuzzy shade matching and `pgvector` for swatch similarity/dupe search.

**Finishes:** shades carry `shade.finishes text[]` (canonical, primary first) plus the legacy `shade.finish` (identity key, kept for backward compat). At runtime the admin-managed `finish_type` table is the source of truth for which finishes are valid, and `finish_normalization` holds the alias spellings; both are loaded together (one cached query) by `loadFinishCatalog()` in `packages/functions/src/lib/finishes.ts`, so a finish type created only in the admin UI is fully usable (parsing, validation, filtering, form options). `CANONICAL_FINISHES` in `packages/shared` holds the built-in seeded defaults, used for typing (`PolishFinish`) and as the fallback when the DB/reference API is unavailable; a test keeps it equal to the migration seeds. Request `tags` on polish create/update never modify catalog finishes (shades are shared); only ingestion connectors parse finishes from product tags. **Catalog write rule (#224):** user-supplied `finishes`/`finish` and color fields (`color`, `vendorHex`, `detectedHex`, `nameHex`) are written to a shade only when the request creates it; adopting, matching or updating an existing shared shade never changes them (not even to fill an empty value), except that a user may keep correcting their own private `user_submitted` shade. A `finish_type` still used by any shade (`shade.finishes` or legacy `shade.finish`) or `finish_normalization` alias cannot be deleted: `DELETE /api/reference-admin/finishes/{id}` returns 409 with the usage counts (`FinishTypeInUseResponse`). Renaming one (`PUT` with a new `name`) cascades in one transaction: `finish_type.name` and the `finish_normalization` rows pointing at it change in a single statement (non-deferrable FK), `shade.finishes`/`detected_finishes` entries are rewritten, and an alias old → new name is added; the legacy `shade.finish` is never rewritten because it is the raw vendor dedup key. A name another type already has (any case) returns 409 `FinishTypeNameTakenResponse`. AI prompts (vision hex/finish detection, sync and batch, and label OCR) list the finishes from `finishNamesForPrompt(loadFinishCatalog())`, falling back to `CANONICAL_FINISHES`. **Finish families (#320, D10):** each `finish_type` has an optional `family` (`FINISH_FAMILIES` in `packages/shared`: solid, shimmer, holo, glitter, matte, thermal, glow; CHECK-constrained, migration 20261018175839000_finish-type-family seeds the built-ins), editable in the admin Configuration tab. `loadFinishCatalog()` returns it as `families` (`buildFinishFamilyMap`, catalog rows over the static `DUPE_FINISH_FAMILIES` fallback, which a test keeps equal to the seeds), and the dupe endpoints and the web's client-side add-guard check grade with it; a finish without a family still grades `unknown` and is never penalized. The API always sends `family` (`null` = none); a payload without the key keeps the built-in family. **Product text (#352):** every connector also stores `descriptionText` and `descriptors` in `external_product.normalized_json` (`lib/product-text.ts`; no shade column, reached via `shade_source_product`, never in user-facing responses). Ingestion resolves finishes by precedence in `lib/finish-text.ts`: tags win, then descriptors, then description text (catalog names + aliases with negation/cross-sell/brand guards); text-derived finishes only fill a shade that has none. The vision prompt gets the text as a labeled vendor hint (`PROMPT_VERSION` `vision-direct/2026-10-v3`).

**Mobile app (#109):** `apps/mobile` is an Expo Router app whose route groups mirror the web (`src/app/(app)/(tabs)` = Collection / Search / Add / Profile behind `Stack.Protected`, `sign-in` outside), with the web's three auth modes (dev bypass `Bearer dev:<id>`, Entra External ID via `expo-auth-session` authorization code + PKCE with tokens in `expo-secure-store`, not configured), every session checked with `POST /api/auth/validate`, and a typed client mirroring `apps/web/src/lib/api.ts` (`src/api/client.ts`). Native Rapid Add (Add tab) scans GTINs on device with `expo-camera` (validated by the shared `barcode/gtin.ts`; iOS's 0-prefixed EAN-13 is sent as the printed UPC-A because `barcode.gtin` lookups are exact), uploads tagged frames with retry, and answers from the read-only `POST /api/capture/{id}/check` (own it / on wishlist / near-dupe / new / pick / not found); it never adds until the user taps Add (`PUT /api/polishes/{shadeId}`, or `finalize` for a shade-less SKU). Colors come from `packages/shared/src/constants/design-tokens.ts`, generated from the web's `globals.css` by `npm run sync:design-tokens` (CI `--check`). The root `package.json` `overrides` pins `react`/`react-dom` to one version (React Native's renderer must match React exactly). The Collection tab starts with a Home panel (counts, "Pick for me" mirroring `apps/web/src/lib/pick-for-me.ts` in `apps/mobile/src/lib/pick-for-me.ts`, one-tap mani log) and the Manis tab is the mani log; the first pages of the Collection, Home counts and mani log are cached per user in AsyncStorage (stale-while-revalidate, wiped on sign-out) and the signed-in user is stored so an offline launch opens the saved data. `/match` matches a camera or library photo with the web's #373 rules (`src/lib/photo-match.ts`), and owned polishes get the private nail photo on the detail screen while the mani log takes optional photos (#396). Private media stays in memory only: owner-scoped `v3` URLs are fetched with the bearer token from the API origin only, held as an in-memory data URI (small LRU, `expo-image` `cachePolicy="none"`, cleared on sign-out), never written to a disk cache or AsyncStorage, and never logged (`src/lib/private-image*.ts`). CI's Mobile job also runs `expo export` for iOS and Android. See `apps/mobile/README.md`.

**Inventory status:** each `user_inventory_item` has `status` (`owned | wishlist | destash | archived`, CHECK-constrained; `PolishStatus` / `POLISH_STATUSES` in `packages/shared`), `tried_at`, `last_worn_at` and `wear_count` (migration 20261017061336791_inventory-status). Ownership is only ever `status = 'owned'` (web: `isOwnedPolish` in `apps/web/src/lib/inventory-status.ts`); never infer ownership or wishlist from `quantity`. "Untried" is derived (`owned AND tried_at IS NULL`, `Polish.isUntried`), not a status. `GET /api/polishes` filters with `status=` (comma list) and `untried=true`; create/update validation lives in `packages/functions/src/lib/inventory.ts`. Status rules (decision D5): a new row without `status` is `owned` (only an explicit `quantity: 0` gives `wishlist`); running out archives (`status: "archived"`, reason `used_up`/`decluttered` stored as an `inventory_event`, see `planArchiveEvent`), never wishlists; only an explicit Rebuy / ♡ moves an archived polish to the wishlist; CSV-import rows with quantity 0 and no status wait for the user's wishlist/archived choice. The `/polishes` ownership filters are a single `status=` URL list (`apps/web/src/lib/polish-list-url.ts`).

**Shade hexes:** each shade has `vendor_hex` (vendor product data), `detected_hex` (AI vision on the product image) and `name_hex` (from the color name). Every `detected_hex` write also records provenance (`detected_hex_confidence`, `detected_hex_method`, `detected_hex_model`, `detected_hex_prompt_version`, `detected_hex_at`; migration 20261017024958000_shade-detected-hex-provenance) via `packages/functions/src/lib/hex-provenance.ts`, and `shade.hex_agreement` is a generated column holding the OKLAB distance vendor ↔ detected. Bump `PROMPT_VERSION` in `ai-color-detection.ts` whenever the vision prompt changes. **Snap step (behind `HEX_DETECTION_SNAP_ENABLED`, default off):** every `detected_hex` write path (ingestion sync detection, the batch-submit fallback, the batch poller apply step and admin `recalc-hex`) runs `snapDetectionToImage` from `packages/functions/src/lib/hex-snap.ts` after `detectHexWithAzureOpenAI`: it re-reads the *same image the model was shown* (`lib/detection-image.ts`: data URI, `/api/images/{id}` proxy id decoded to its blob, or the vendor URL; the poller takes each row's image from the batch input file) and replaces the model's hex with the nearest palette chip measured from it (`extractPaletteCandidates`) when one is within `HEX_SNAP_MAX_DISTANCE` (default 0.10). Snapped rows are stored with `detected_hex_method = 'vision-snap'`; a detection with no chip close enough, or whose image cannot be read, keeps the raw hex and `vision-direct`. The prompt and `PROMPT_VERSION` do not change. The eval `blind-snap` strategy imports the same module. Display uses `resolveDisplayHex` (vendor > detected > name); `resolveDisplayHexDetailed` in `packages/shared` adds the source, agreement and a review flag (disagreement > 0.10 MEDIUM, or a caller-marked suspicious vendor hex). Admins review weak detections with `GET /api/polishes-admin/hex-review`, and build hand-picked ground truth for the hex-detection eval in the admin console's Hex Labeling tab (canvas eyedropper over a shade's catalog images → `color_training_sample` rows with `source_type = 'manual'`, one per shade, via `/api/hex-labels-admin/*`; migration 20261017170047543_hex-ground-truth-labels). Saving a label never writes `vendor_hex`/`detected_hex`. **Promote to vendor hex (#321, D12):** the only exception is the explicit, confirmed per-label admin action `POST /api/hex-labels-admin/labels/{id}/promote` (`lib/vendor-hex.ts`; approved labels only, never private `user_submitted` shades), which copies the label's hex to `vendor_hex` with provenance (`vendor_hex_source` `vendor | manual_label`, `vendor_hex_label_id`, `vendor_hex_set_by_user_id`, `vendor_hex_set_at`, `vendor_hex_previous`; migration 20261020024540860_shade-vendor-hex-provenance) and an `admin_audit_event` row in the same transaction; Undo (`DELETE …/labels/{id}/promote` or `DELETE …/shades/{shadeId}/promotion`) restores `vendor_hex_previous`. Deleting a promoted label keeps the hex (FK ON DELETE SET NULL). **D12 ingestion rule:** every connector `vendor_hex` write goes through `planIngestedVendorHex` on a `FOR UPDATE` read and never replaces a `manual_label` hex; the incoming vendor value goes to `vendor_hex_previous` so Undo restores current vendor data. The provenance is admin-only (not in user-facing polish responses); display still uses vendor > detected > name. `eval:hex:populate` exports labels as `manual` cases scored on the sampled image (which needs a public vendor URL from `source_image_url`). Canvas reads rely on `/api/images/{id}` CORS: allowed origins get `Access-Control-Allow-Origin`, every image response has `Vary: Origin`, and private `v3` responses never get `*`.

**Catalog thumbnails:** ingestion (`uploadSourceImageToBlob` → `ensureImageVariants`) writes pre-generated square WebP thumbnails next to each catalog blob, `<blob>.c<IMAGE_VARIANT_CROP_VERSION>.w<size>.webp` for `IMAGE_VARIANT_SIZES` (64/128/256/512, `packages/shared/src/constants/image-variants.ts`). Studio shots on a flat background are cropped to a square around the product (trim the background, `planImageVariantCrop` in `packages/functions/src/lib/image-variants.ts`); other photos are center-cropped. Bump `IMAGE_VARIANT_CROP_VERSION` whenever the crop or rendering changes (variant blobs are never rewritten) and run the backfill. The image proxy snaps public `?w=n&h=n&fit=cover&fm=webp` requests up to that ladder and serves the variant blob, falling back to rendering it from the original (same `renderImageVariant`) when it is missing; private `v3` media has no variants. The web renders catalog thumbnails with `SwatchThumbnail` (`buildSwatchThumbnailSources`: 1x/2x `srcSet`). Changing the ladder needs a backfill (`POST /api/images-admin/variants/backfill`, looped by `npm run backfill:image-variants`).

**Catalog galleries:** a shade's catalog images are its `swatch` rows (`source_product` = primary, `source_gallery` = additional) over `image_asset` rows deduped by `(owner_id = data source, checksum_sha256)`. After linking a product's images, ingestion makes the shade's `source_gallery` swatches from that data source exactly the product's current images (`pruneStaleGallerySwatches` in `packages/functions/src/lib/gallery-dedupe.ts`; only when every image was stored this run, skipped when another product of the same source maps to the shade; `source_product`, other sources, user media, and swatches whose image has a `color_training_sample` label or that have `color_features` are never touched; `image_asset` rows and blobs are kept). Existing duplicates (the same picture stored twice under different checksums by older ingests) are removed by the admin perceptual-match cleanup `POST /api/images-admin/gallery-dedupe` / `npm run dedupe:gallery-images`. Each `image_asset` row stores a perceptual fingerprint (`perceptual_hash`, `thumb_fingerprint`, `image_width`, `image_height`, all-or-nothing; migration 20261018234237112_image-asset-perceptual-fingerprint), computed by `uploadSourceImageToBlob` from the stored bytes and backfilled by the cleanup endpoint for images reused by URL without a download. Ingestion does not link an additional image as a `source_gallery` swatch when it near-duplicates an image already linked for the product in that run (`planProductGalleryLinks`, `INGEST_NEAR_DUPLICATE_THRESHOLDS`: dHash ≤ 64, thumbnail MAD ≤ 20, aspect ≤ 3%, measured on Cracked Polish: catches small same-aspect re-crops and same-pose re-shoots, not crops to another aspect) or the product already links `GALLERY_MAX_IMAGES_PER_SHADE` gallery images; skipped images are still stored and kept in the prune keep-set, a swatch an earlier run linked for one is unlinked (unless protected or the shade is shared with another product of the source), and the image AI hex detection chose (`chooseUploadedImageForDetection`, which still sees every upload) is always linked.

**Barcodes (#21, #325):** a scanned code resolves in one round trip. `lib/barcodes.ts` `normalizeGtin` gives every code one canonical key (UPC-A = 0-prefixed EAN-13 = 00-prefixed GTIN-14 = its UPC-E; EAN-8/13 as is; SKU junk and odd lengths rejected; a wrong check digit is kept and logged, not rejected). Catalog `barcode` rows hang off a SKU of the shade (`barcode.source` `ingestion`/`backfill`, `external_product_id`; migration 20261019030000000_barcode-provenance-and-user-barcodes): Shopify-style ingestion links the product GTIN and every variant barcode (`materializeProductBarcodes`), and `POST /api/barcodes-admin/backfill` (`npm run backfill:barcodes`, dry run by default) does it for products stored earlier. A GTIN belongs to one shade (`barcode.gtin` UNIQUE): the first shade keeps it, later claims are skipped and logged in the job log. The capture resolver tries catalog barcodes, then the caller's own learned `user_shade_barcode`, then connector products' raw `external_product.gtin` → `shade_source_product` → one active shade (fallback until the backfill has run). A `barcode` frame with a valid on-device decoded `quality.gtin` skips OCR and its response carries `check` (the read-only verdict, with a display `hex`). A session that scanned an unknown GTIN and was matched another way (label, candidate, typed name), or a manual add carrying `barcode` (`POST /api/polishes`), remembers the GTIN in `user_shade_barcode`, private to that user and never in the shared catalog.

**Color families (#103):** `classifyColorFamily` in `packages/shared/src/color/color-family.ts` bins a shade's display hex by OKLCH lightness/chroma/hue into red, pink, coral, orange, yellow, green, teal, blue, purple, nude, brown, grey, black or white; `multichrome` comes from finishes (`multichrome`/chameleon/color-shift; duochrome is binned by hex). Postgres mirrors it in `shade_color_family()` and stores it as the generated column `shade.color_family` (migration 20261017061637910_add-shade-color-family), which `?family=` filters on in `GET /api/polishes` and `GET /api/catalog/search`. **Color-distance sort:** `GET /api/polishes?nearHex=RRGGBB[,…]` (≤ 24, `lib/near-hex.ts`) ranks any filtered list by OKLAB distance from the display hex to the nearest target (nulls last, shade id tiebreak) and returns `colorDistance` per row; it ranks on the STORED GENERATED `shade.oklab_l/a/b` (migration 20261023001520034_shade-display-oklab, `hex_to_oklab` of the display hex trimmed like `color_family`), and `tests/near-hex.unit.test.cjs` keeps `hex_to_oklab()` equal to the shared `hexToOklab`. Clients never rank a fetched page by color: web color search, polish detail related shades, Looks gap queries and mobile By color (catalog) ask the API; client-side ranking is only for the fully loaded owned collection. `tests/color-family.unit.test.cjs` keeps the SQL threshold constants equal to `COLOR_FAMILY_THRESHOLDS`; changing a bin needs a new migration that redefines the function and rewrites the rows.

**Product categories (#349, #347; decision D23, plan `docs/plan-catalog-hygiene.md`):** `shade.product_category` (`color | topper | top_coat | base_coat | treatment | accessory`, default `color`; `PRODUCT_CATEGORIES` / `ProductCategory` in `packages/shared`, a test keeps the migration CHECK equal) plus `product_category_source` (`rule | admin`; migration 20261022190729000_shade-product-category). `classifyProductCategory` in `packages/functions/src/lib/product-category.ts` mirrors `docs/queries/catalog-hygiene-audit.sql` rule for rule (accessory from name/color name/title/product type or an explicit tool type tag, never free tags, with ambiguous words such as jewels/foils/studs counting only under a non-polish product type; topper beats coat wording; then base coat, top coat, treatment, read from the name/title/product type before the tags; else color): change the audit query first, then the classifier. Every connector gates products with `classifyIngestedProduct` (accessories and the June tag blocklist skipped; coats/treatments ingested with their category) and materialization writes the rule category, never over an `admin` one. Vision hex detection (sync, batch, recalc-hex) runs on `color` only. The admin backfill `POST /api/shades-admin/product-category/backfill` (dry run by default; `npm run backfill:product-category`) re-classifies the catalog, sets `status = 'excluded'` on accessories nobody holds (held ones are listed), and with `clearTopperDetectedHex` clears suspicious topper `detected_hex` values; every change is logged in `shade_category_change` (before/after, run id) so it can be undone. Admin override: `PUT /api/shades-admin/{id}/product-category` (sticky). Surfaces (D-C): accessories and `excluded` shades are visible only to holders (`POLISH_VISIBLE_SQL`, import matching) and never in catalog search; color search, gaps, photo match, hex review/labeling are color-only; dupes compare color↔color and topper↔topper only (`areDupeComparableCategories` in the shared dupe rule); Pick for me never picks a non-color main polish (pair-it may add a topper); stats count coats/treatments in spend only and drop accessories; the mani log prefills roles from the category (`manicureRoleForCategory`). `?category=` filters `GET /api/polishes` and catalog search; responses and the export carry `productCategory`.

**Telemetry:** Functions and web both report to the same workspace-based Application Insights (see `docs/observability-plan.md`). The web SDK is lazy-loaded after hydration, sends W3C `traceparent` only to the API host, tags telemetry with the internal user id (never email), and redacts `/api/images/{id}` capability ids and shared wishlist/look tokens; route-group `error.tsx` files and `app/global-error.tsx` report render errors. M2 success metrics (D19): browser events `dupe.warning_shown` / `dupe.warning_outcome` / `mani.logged` / `import.completed` / `onboarding.step_clicked` from `apps/web/src/lib/metrics-events.ts`, plus the weekly read-only query `docs/queries/m2-metrics.sql`. Prod alerts (Terraform, `alerts_enabled`) email `alert_email` on API 5xx, exception spikes (server + browser), `ingestion.job_failed` events (emitted by `markIngestionJobFailed`), the daily cap being hit, and failing availability tests (web home page, `GET /api/reference/finishes`).

**Buy from brand (#267):** polish list/detail and catalog search/shade responses carry an optional `buyUrl` — the brand product page from the connector-stored `external_product.normalized_json ->> 'productUrl'`, reached through `shade_source_product` (written by ingestion materialization; migration 20261017061344201_add-shade-source-product). `packages/functions/src/lib/buy-link.ts` validates (absolute http/https only, no credentials) and picks one product deterministically (enabled source, then latest `last_seen_at`, then latest `fetched_at`, then highest id). No affiliate parameters; `applyAffiliateParams()` is the one place to add them. The same chosen product's vendor list price rides along as optional `buyPrice` / `buyCurrency` / `buyPriceSeenAt` (`selectBuyFromBrandLink` returns `{ url, price?, currency?, priceSeenAt? }`; only when both a valid amount and an ISO 4217 currency are stored; `priceSeenAt` = `external_product.fetched_at`; never the user's `purchase_price`, never converted or summed across currencies). Connectors write `price` (decimal string) + `currency` into `normalized_json` via `lib/product-price.ts`: Shopify-style stores take the lowest available variant price (else the lowest variant) and the store currency from `data_source.metadata.currency`, else the shop's `/meta.json`, else null (USD is never assumed); MakeupAPI keeps its ISO `currency` only; OpenBeautyFacts has none. Older rows: `npm run backfill:product-price`. The web renders it via `BuyFromBrandLink` with `rel="noopener noreferrer nofollow"` (with the price and an "as of" hint on wishlist/catalog rows and the detail page, per-currency subtotals on the Looks shopping list); mobile shows the price under the detail screen's buy button.
**Private media:** user photos (today the per-item nail photo, #270) live in `USER_MEDIA_CONTAINER`, referenced by `image_asset` rows with `owner_type = 'user'`, and are only ever exposed as owner-scoped `v3` image proxy URLs that require the owner's bearer token (web: `PrivateImage`). The mobile app (`apps/mobile`: nail photo on polish detail, mani photos) fetches `v3` URLs only with the bearer token and only from the API origin, keeps the bytes as in-memory data URIs (`expo-image` `cachePolicy="none"`, never a disk cache or AsyncStorage) and clears them on sign-out (`src/lib/private-image-loader.ts`). Every upload is re-encoded server-side so no EXIF/GPS metadata is stored; never return raw blob URLs or public `v2` ids for user media. Rows orphaned by cascade deletes outside the API (an `app_user` delete, an admin merge removing a duplicate inventory row) are removed by the daily `orphan-media-sweep` timer (#319, `src/lib/orphan-media-sweep.ts`): an `owner_type = 'user'` asset whose `captured_at` is older than `ORPHAN_MEDIA_SWEEP_GRACE_SECONDS` (rows without `captured_at` are never swept) that no foreign key references (discovered from `pg_constraint` each run, so new referencing tables are covered automatically) loses its blob first, then its row; only blobs in `USER_MEDIA_CONTAINER` under the owner's `{ownerId}/` prefix, and used by no other `image_asset` row, are ever deleted.
**Wear stats:** `user_inventory_item.wear_count` and `last_worn_at` are derived from the mani log (`manicure` / `manicure_polish`, keyed by `shade_id`): `packages/functions/src/lib/manicure.ts` `recomputeWearStats()` rewrites them for the affected shades after every manicure create/edit/delete (and after polish create/update), never by incrementing or decrementing. `tried_at` is only filled from the earliest wear when NULL, never cleared by the log.
**Shareable wishlist (#268):** an opt-in, revocable public read-only page for a user's `status = 'wishlist'` items, entirely behind the server flag `SHAREABLE_WISHLIST_ENABLED` (default off, pending roadmap §6 decision 2; all `/api/wishlist-share*` and `/api/wishlist/{token}` routes 404 with `code: "feature_disabled"` while off, and the web card hides itself on that response). One `wishlist_share` row per user (migration 20261017064751368_wishlist-share) stores only a salt and `SHA-256(token)`; the token is `HMAC(subkey of IMAGE_PROXY_SIGNING_KEY, user_id:salt)`, re-derivable by the owner but not from a DB leak. The public payload is an explicit allowlist (owner-chosen display name; brand, shade, finishes, display hex, public `v2` catalog image) — never ids, email, notes, prices, quantities, private `v3` media, or the owner's private `user_submitted` shades. Anonymous reads are rate-limited per IP and per token with in-memory token buckets (`src/lib/rate-limit.ts`, best effort per instance).
**Shareable looks:** the same pattern for one saved look (`user_look`): an opt-in, revocable public read-only page at `/l/?token=…`, entirely behind the server flag `SHAREABLE_LOOKS_ENABLED` (default off in every environment; `/api/look-share` and `/api/look/{token}` 404 with `code: "feature_disabled"` while off, and the Looks page hides its Share link controls). One `look_share` row per saved look (migration 20261023001607416_look-share; composite FK `(user_look_id, user_id)` pins it to the look's owner, and deleting the look deletes the link) stores a salt, `SHA-256(token)`, a per-link display name and `revoked_at`; the token is `HMAC("look-share:v1" subkey of IMAGE_PROXY_SIGNING_KEY, user_id:user_look_id:salt)`, a different subkey from the wishlist's. Revoking keeps the row so the old link answers 410 `share_revoked`; sharing again mints a new token. The public payload (`toPublicLook` in `packages/functions/src/lib/look-share.ts`) is an allowlist: display name, template id, vibe (occasion/mood/finish), and per step the role and hex, plus brand, shade, finishes and a public `v2` catalog image only when the step's shade is a public catalog shade (`status = 'active'`, not an accessory, not merged); every other step is a plain color chip. Never ids, email, ownership (owned vs to buy, "owned only"), notes, prices, the saved snapshot's free text, or private `v3` media; the page names the look and steps from the built-in templates and derives application order and finish notes from the payload. Anonymous reads are rate-limited per IP and per token like the wishlist (separate buckets).

**Collection stats:** `GET /api/stats/collection` (`packages/functions/src/lib/collection-stats.ts`) aggregates the caller's inventory in five `user_id`-scoped SQL queries. Money is grouped by `purchase_currency` and never summed across currencies (`null` currency is its own group); spend counts `owned`/`destash`/`archived` rows with a price, and the month bucket falls back from `purchase_date` to the UTC `created_at` date. Cached per user for 60s in Redis; `invalidatePolishCachesForUser()` (`lib/polish-cache.ts`) drops the entry, so any new inventory or mani-log write path must call it.

**Backups:** all in Terraform (`infrastructure/main.tf`, see `infrastructure/README.md` → Backups & Restore), nothing geo-redundant. Postgres has 35 days of point-in-time restore. The app storage account has blob versioning, change feed and blob + container soft delete, with a management policy that expires old versions. That account also holds the live Terraform state in its `tfstate` container, so never remove that container. In prod (`backup_vault_enabled`) an Azure Backup vault takes weekly Postgres and daily `nail-photos` backups, and `CanNotDelete` locks cover Postgres, the storage account and the vault (`delete_locks_enabled`). Key Vault has purge protection. The vault role assignments and the locks need User Access Administrator, so the first apply that adds them runs locally, not in CI.

**Auth:** Azure AD B2C / Entra External ID (tenants and the web app registration provisioned outside Terraform via portal; only the web app's service principal can be Terraform-managed, opt-in per environment with `manage_ciam_service_principal`, through the `azuread.ciam` provider and a GitHub-OIDC deployer app in the CIAM tenant — see `infrastructure/README.md`). Functions read `AZURE_AD_B2C_TENANT` and `AZURE_AD_B2C_CLIENT_ID` from environment. Token validation is JWT-based via the `/api/auth/validate` endpoint. **Web token renewal:** every API call gets its token from MSAL `acquireTokenSilent` (renewed within 5 min of expiry; `getFreshAccessToken()` in `apps/web/src/lib/auth-token.ts`), and any silent failure redirects to sign-in (30 s loop guard, `lib/token-renewal.ts`). Hidden-iframe renewal uses `/blank.html` (MSAL v5 redirect bridge, script copied from `@azure/msal-browser` before dev/build), which must be an SPA redirect URI on the Entra app registration for every web origin. `app_user.role` is re-synced from the token's Entra `roles` claim on every sign-in, so admin is granted in Entra (app role `admin`), never edited in the app. **Admin user management (#45):** `/api/users-admin*` (`admin-users.ts`, `lib/admin-users.ts`; migration 20261018180032156_admin-user-management) lists/searches users, edits the handle and suspends/reactivates accounts; a suspended account (`app_user.suspended_at`) gets 403 `account_suspended` from `withAuth`/`withAdmin` (read via `to_jsonb(app_user.*)` so auth survives an un-migrated DB), an admin cannot suspend themselves, and every change and account merge writes an `admin_audit_event` row (who, what as before/after, when, target) in the same transaction. **Sign-in methods / password reset (#45, `docs/admin-password-reset.md`):** each environment has one External ID tenant (email + password, Google, Facebook); one email address is one Entra user with exactly one sign-in method (Entra sends a second sign-up with the same address to the existing method), and SwatchWatch stores no passwords. Reset is never done by the app: email + password users use "Forgot password?" on the Microsoft sign-in page, Google/Facebook users reset with that provider, and admins get copyable instructions plus an Entra admin center link per identity in `UserDetailDialog` (`apps/web/src/lib/entra-admin-links.ts`; Entra logs admin resets in its own audit log). Suspend is the lockout tool.

## Key Conventions

- **TypeScript strict mode everywhere.** Base config in `tsconfig.base.json` (ES2022, bundler resolution). Each package extends it.
- **Azure Functions v4 programming model:** Register HTTP triggers with `app.http()` in individual files under `packages/functions/src/functions/`. Each file exports handler functions and registers routes at module scope. Example pattern from `polishes.ts`:
  ```ts
  app.http("polishes-list", {
    methods: ["GET"],
    authLevel: "anonymous",
    route: "polishes/{id?}",
    handler: getPolishes,
  });
  ```
- **Shared types** live in `packages/shared/src/types/` and are re-exported from `packages/shared/src/index.ts`. The canonical domain types are `Polish`, `PolishFinish`, `User`, `AuthProvider`, `VoiceProcessRequest`, `VoiceProcessResponse`, etc. When adding new domain types, add them here and re-export.
- **Web app** uses `@/*` path alias pointing to `apps/web/src/*`. Styling uses Tailwind v4 via `@tailwindcss/postcss`.
- **UI components:** shadcn/ui primitives in `apps/web/src/components/ui/`. Custom components in `apps/web/src/components/`. Add new shadcn components with `cd apps/web && npx shadcn@latest add <name>`.
- **Color utilities:** `apps/web/src/lib/color-utils.ts` provides Hex↔HSL↔RGB↔OKLAB conversions and perceptual `colorDistance()`. Use OKLAB for any color matching/sorting logic. Pure color rules shared by web and mobile live in `packages/shared/src/color/` (OKLAB, color families, dupes, `harmonies.ts` harmony palettes, `pair-it.ts` "Pair it"); `apps/web/src/lib/color-harmonies.ts` is a re-export shim, so add new harmony logic to shared, not the web.
- **Mock data:** All pages now use the live API. The old `mock-data.ts` is no longer used. Dev DB is seeded with realistic data via migration 003.
- **Infrastructure as Code:** All Azure resources defined in `infrastructure/main.tf`. Resource naming follows `${base_name}-${environment}-{resource}-${random_suffix}` convention.

## Environment Variables

Where each set lives: Functions → `packages/functions/local.settings.json` (copy `local.settings.json.example`, which lists every setting in the groups below; Terraform-managed app settings + Key Vault references in Azure). Web → build-time `NEXT_PUBLIC_*` (`apps/web/.env.local` locally, since Next.js reads env files from `apps/web` only; `.github/workflows/deploy.yml` in CI). Mobile → `apps/mobile/.env.local` (from `.env.example`). Migrations → `npm run migrate` / `migrate:down` copy every `local.settings.json` value into the environment first (overriding exported or inline variables of the same name, `PG*` included), then use `DATABASE_URL` if set, else `PG*`; to target another database export `DATABASE_URL` (the example defines none). Infra → GitHub environment variables/secrets read by `deploy-infra.yml`. Full tables with defaults: `packages/functions/README.md` → Environment Variables, `apps/web/README.md`, `apps/mobile/README.md`, `infrastructure/README.md`. The `NEXT_PUBLIC_*` entries in `local.settings.json.example` are a convenience copy; the Functions host ignores them. When adding a variable, put it in the matching group here, in the Functions README table and in `local.settings.json.example`. Flags are on only for the exact value `true`.

### Functions: runtime, database, auth

- `FUNCTIONS_WORKER_RUNTIME` (`node`), `AzureWebJobsStorage` (host storage; Azurite locally). `FUNCTIONS_NODE_BLOCK_ON_ENTRY_POINT_ERROR=true` (Terraform-managed) makes import failures fail startup instead of route 404s. `WEBSITE_HOSTNAME` / `WEBSITE_INSTANCE_ID` are set by Azure, never by us: `src/lib/runtime-env.ts` uses them to detect a hosted instance.

Pool: `PG_POOL_MAX` (10), `PG_IDLE_TIMEOUT_MS` (30000), `PG_CONNECTION_TIMEOUT_MS` (15000), `PG_QUERY_MAX_RETRIES` (2, retry-safe `SELECT` / `UPDATE ingestion_job` on connection timeouts), `PG_QUERY_RETRY_BASE_MS` (250). `DATABASE_URL` is read only by `npm run migrate` and `migrate:down`, ahead of `PG*` (an exported value works because `local.settings.json` normally has none); the DB scripts (`eval:hex:populate`, `backfill:product-text`) read `PG*`.

### Functions: storage, image proxy, private media

- `AZURE_STORAGE_CONNECTION` — storage account (Azurite locally). Unset: ingestion keeps source image URLs, the orphan sweep is skipped.
- `SOURCE_IMAGE_CONTAINER` (`source-images`, catalog images + variants; the only container `v2` ids read), `USER_MEDIA_CONTAINER` (`nail-photos`, private user media; the only container `v3` ids read, #227), `CONNECTOR_RAW_CONTAINER` (raw connector snapshots + ingestion catalog cache; unset = no-op; legacy name `RAW_SNAPSHOT_CONTAINER` still read but deprecated).
- `IMAGE_PROXY_SIGNING_KEY` — secret (>= 32 chars) that HMAC-signs `/api/images/{id}` capability ids (`src/lib/image-proxy.ts`) and roots shareable wishlist and look tokens. Fails closed when unset (image URLs omitted, proxy refuses requests) unless dev bypass is active, which uses an ephemeral per-process dev key. Terraform generates it into Key Vault (`image-proxy-signing-key`).
- `IMAGE_PROXY_ID_TTL_SECONDS` — minimum lifetime of public `v2` ids (default `259200` = 3 days, clamped 1h–30d; keep above the AI batch completion window plus poller lag, since the poller re-reads the same ids for the snap step and an expired id just keeps the raw `vision-direct` hex).
- `IMAGE_PROXY_PRIVATE_ID_TTL_SECONDS` — minimum lifetime of owner-scoped `v3` ids (default `3600`, clamped 300–86400, bucketed to 15 minutes).
- `IMAGE_PROXY_LEGACY_ID_ACCEPT_UNTIL` — optional ISO-8601 cutoff for accepting legacy non-expiring `v1` ids (unset = rejected).
- Orphan media sweep (#319, `src/lib/orphan-media-sweep.ts`): `ORPHAN_MEDIA_SWEEP_SCHEDULE` (NCRONTAB, default `0 17 3 * * *`), `ORPHAN_MEDIA_SWEEP_GRACE_SECONDS` (minimum `captured_at` age, default `86400`, clamped 3600–2592000), `ORPHAN_MEDIA_SWEEP_BATCH_SIZE` (per scan query, default `100`, clamped 1–1000), `ORPHAN_MEDIA_SWEEP_MAX_PER_RUN` (default `2000`, clamped 1–20000; the rest wait for the next run).

### Functions: Azure OpenAI and hex detection

- Client (`src/lib/azure-openai-config.ts`): `AZURE_OPENAI_ENDPOINT` + `AZURE_OPENAI_KEY` (`api-key` header); always the Azure OpenAI resource directly (APIM gateway removed, D25).
- Deployments: `AZURE_OPENAI_DEPLOYMENT` (fallback for all), `AZURE_OPENAI_DEPLOYMENT_HEX` (sync vision detection), `AZURE_OPENAI_DEPLOYMENT_HEX_BATCH` (batch; → `_HEX` → `AZURE_OPENAI_DEPLOYMENT`), `AZURE_OPENAI_DEPLOYMENT_LABEL` (label OCR extraction; → `_HEX` → `AZURE_OPENAI_DEPLOYMENT`).

- Sync pacing: `HEX_DETECTION_CONCURRENCY` (default `4`, max `32`; DB writes stay sequential; capped by the deployment's TPM quota, so raise together with capacity), `HEX_DETECTION_DELAY_MS` (pause after each call per slot, default `1000`, max `60000`, `0` disables; 429s are still retried with `Retry-After`).

- Batch pipeline: `HEX_DETECTION_BATCH_MIN_IMAGES` (records before switching to batch, default `5`), `HEX_DETECTION_BATCH_MAX_IN_FLIGHT` (pending batches per job before pausing for `awaiting_ai`, default `20`, clamped 1–100), `AZURE_OPENAI_BATCH_API_VERSION` (default `2025-03-01-preview`), `AZURE_OPENAI_BATCH_COMPLETION_WINDOW` (default `24h`), `INGESTION_AI_BATCH_POLL_SCHEDULE` (NCRONTAB, default `0 * * * * *`), `INGESTION_AI_BATCH_MAX_POLL_JOBS` (default `10`), `INGESTION_AI_IMAGE_PROXY_ORIGIN` (public origin for the `/api/images/{id}` URLs sent to Azure OpenAI; defaults to `https://$WEBSITE_HOSTNAME`).

## Git Workflow

**GitHub Flow** with **Conventional Commits**. See `CONTRIBUTING.md` for full details.

- **Branches:** `<type>/<issue#>-<description>` off `dev` (e.g., `feat/12-catalog-search`, `fix/34-color-wheel-safari`); `scripts/agent-worktree.sh` branches from `dev` by default
- **Commits:** `feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:` prefixes
- **PRs:** Squash merge into `dev`. PR title = conventional commit message. Reference issues with `Closes #N`.
- **Integration branch (`dev`, decision D24):** feature PRs target `dev`. An unattended (overnight) session may squash-merge its own PR into `dev` once CI is green and every review thread is fixed or answered; only the owner merges `dev → main` (a release PR with a merge commit). Closing keywords fire only on `main`, so issues shipped to `dev` are closed by hand after the release (see the overnight runbooks in `docs/`).
- **Issues:** Use GitHub Issue templates (Feature, Bug, Chore). Add scope labels (`web`, `mobile`, `functions`, `infra`).

## Agent Worktrees

When working on a branch that isn't the current checkout, use **git worktrees** instead of switching branches. This avoids dirty-file conflicts (e.g., `.claude/settings.local.json`) and lets multiple agents work in parallel.

```bash
# Create a worktree for a new branch (defaults to branching from dev)
scripts/agent-worktree.sh feat/42-new-feature

# Branch from main instead
scripts/agent-worktree.sh fix/99-hotfix main

# Clean up when done
git worktree remove ../swatchwatch-worktrees/feat/42-new-feature
```

Worktrees live in `../swatchwatch-worktrees/<branch-name>` (sibling to the primary repo root). The script copies local `.env` and `packages/functions/local.settings.json` when present, then runs `npm ci` and builds shared types so the worktree is ready to use immediately.

**Rules:**
- Never switch branches in the primary checkout during agent work — use a worktree.
- Each worktree is independent: changes in one don't affect the other.
- Run `git worktree list` to see active worktrees.
- Remove worktrees after the branch is merged.
